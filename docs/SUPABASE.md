# Backend (Supabase)

Vlocal uses a Supabase project for three things. None of them is needed to run
the app: without network, everything works and the calls fail silently.

| Use | Endpoint | Auth |
| --- | --- | --- |
| Version check and in-app update metadata | edge function `get-latest-version` (reads `app_versions`, `app_config`) | anon key |
| Diagnostic sent by the user from Settings | edge function `submit-feedback` (writes `feedback`) | anon key |
| Declared telemetry | PostgREST upserts into `installs` and `usage_days` | anon key, RLS: insert and update only |
| Admin console (`admin.html` on the landing site) | edge function `admin` (token in `app_config.admin_token`, service role) | admin token |

## Tables

`supabase/migrations/20260906_installs_usage.sql` creates `installs`,
`usage_days`, their RLS policies and the `installs_overview` view used by the
admin console. Apply it in the SQL editor of the project.

The anon role can insert and update rows (PostgREST upsert with
`resolution=merge-duplicates`) but has no select policy: the public key cannot
read anything back. The install identifier is a random UUID generated by the
app, so a row can only be updated by the installation that created it.

## Running your own backend

1. Create a Supabase project, apply the migration.
2. Deploy the edge functions from the landing repository
   (`supabase/functions/admin`) and your own `get-latest-version` and
   `submit-feedback`, or drop the features you do not need.
3. Set `VLOCAL_SUPABASE_URL` and `VLOCAL_SUPABASE_ANON_KEY` in the environment,
   or edit `supabase_config.py`.
